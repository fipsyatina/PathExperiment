# PathExperiment

[English](README.md) · [Polski](README.pl.md) · [Українська](README.uk.md)

![Покрокове розгортання клітинок, відхилення переходів і завершення маршруту в PathExperiment](docs/media/search.gif)

![Панель порівняння доступних алгоритмів у PathExperiment](docs/media/comparison.png)

PathExperiment — настільний C++20 застосунок для створення зважених карт, покрокового спостереження за пошуком маршруту та порівняння алгоритмів за однакових умов. Пошукове ядро не залежить від SFML, тому проєкт є і наочним навчальним інструментом, і стендом для майбутньої навігації юнітів у Ribterra.

[Відкрити сторінку останнього релізу](https://github.com/fipsyatina/PathExperiment/releases/latest), де з'являться готові пакети після публікації. Мова інтерфейсу застосунку — англійська.

## Можливості

- [x] Велике стандартне поле 120 × 80 із клітинками приблизно 8 px
- [x] Дорога, звичайна місцевість, болото, стіна, старт і ціль
- [x] Довільні прохідні клітинки старту `S` та цілі `G`
- [x] Детерміновані Dijkstra, A*, BFS і greedy best-first із рухом у чотирьох напрямках
- [x] Покрокова візуалізація відкритих, опрацьованих і поточних клітинок
- [x] Підсвічування вдалих і відхилених перевірок сусідів та попереднього ланцюжка шляху
- [x] Запуск, пауза, один крок, завершення без анімації та швидкість 1–60 розгортань за секунду
- [x] Вартість, довжина, кількість опрацьованих клітинок і статус пошуку
- [x] Порівняння всіх зареєстрованих алгоритмів за медіаною 31 незалежного запуску після прогріву
- [x] Збереження й завантаження `.pemap`
- [x] П'ять готових карт 40 × 25 і одна карта 120 × 80 у каталозі `maps/`
- [x] Тести алгоритмів і формату карти без графічного вікна
- [x] Реєстр для додавання власних алгоритмів у вихідному коді

## Робочий простір

На панелі зверху розташовані інструменти малювання та роботи з файлами. Інспектор біля карти містить вибір алгоритму, керування пошуком, результати й таблицю порівняння. Наведіть вказівник на клітинку, щоб переглянути її дані. Старт і ціль позначені літерами `S` і `G`.

П’ять прикладів використовують сітки 40 × 25 для коротких експериментів; карта з різною вартістю місцевості займає повне поле 120 × 80. Завантажувач підтримує карти від 1 × 1 до 512 × 512.

## Керування

Ліва кнопка миші застосовує вибраний інструмент. Права повертає клітинку до звичайної місцевості.

Встановлення кінцевої точки на стіну перетворює цю клітинку на звичайну місцевість. Старт і ціль можуть збігатися; тоді маршрут має нуль кроків і нульову вартість.

| Клавіша | Дія |
| --- | --- |
| `1` | Дорога |
| `2` | Звичайна місцевість |
| `3` | Болото |
| `4` | Стіна |
| `5` | Старт |
| `6` | Ціль |
| `Shift` + ліва кнопка | Встановити старт, не змінюючи інструмент |
| `Ctrl` + ліва кнопка | Встановити ціль, не змінюючи інструмент |
| `Space` | Запустити або призупинити пошук |
| `N` | Виконати один крок |
| Кнопка `Finish` | Завершити пошук без анімації |
| `R` | Скинути візуалізацію пошуку |
| `C` | Створити нову звичайну карту 120 × 80 |
| `Tab` | Вибрати наступний зареєстрований алгоритм |
| `B` | Виміряти всі зареєстровані алгоритми |
| `Ctrl+S` | Зберегти карту у файл з унікальною часовою позначкою |
| `Ctrl+O` | Відкрити `.pemap` через системний вибір файлу на Windows; на інших системах завантажити останнє збереження |

Кнопки інтерфейсу дублюють ці дії. Кнопки `<`, `>` і `Load example` дозволяють вибрати та відкрити готовий приклад. Інспектор клітинки показує координати, вартість входу та доступні стан, `g`, `h`, пріоритет, глибину й попередню клітинку.

Помаранчева лінія — поточний кандидат шляху, зелена — фінальний маршрут. Сині клітинки показують опрацьовані гілки, зокрема тупикові; червоні позначки — відхилені переходи до сусідів. Пауза та `N` дозволяють роздивитися кожну перевірку. Відхилення переходу через стіну, вже опрацьовану клітинку або відсутність покращення вартості не означає помилку алгоритму.

Швидкість анімації — 1–60 клітинок на секунду. Кожне розгортання отримує окремий кадр; якщо відображення сповільниться, анімація теж сповільниться, щоб зберегти всі кроки.

Нові карти зберігаються з унікальною часовою позначкою. На Windows каталог збережень — `%LOCALAPPDATA%\PathExperiment\maps`. На Linux застосунок використовує `$XDG_DATA_HOME/PathExperiment/maps`, а якщо `XDG_DATA_HOME` не задано — `~/.local/share/PathExperiment/maps`.

## Збирання

Потрібні CMake 3.28 або новіший, компілятор із підтримкою C++20 та доступ до мережі під час першої конфігурації. CMake автоматично завантажує SFML 3.1.0. Налаштування відповідає офіційному [шаблону SFML із CMake](https://github.com/SFML/cmake-sfml-project), а параметри команд описані в [довіднику CMake](https://cmake.org/cmake/help/latest/manual/cmake.1.html).

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
cmake --install build --config Release --prefix dist/PathExperiment
```

Графічний застосунок і копії потрібних ресурсів будуть у `build/bin/`. Запускайте `build/bin/PathExperiment.exe` на Windows або `build/bin/PathExperiment` на Linux.

На Windows установіть компонент Visual Studio «Desktop development with C++». На Ubuntu для графічної збірки потрібні `libxrandr-dev libxcursor-dev libxi-dev libudev-dev libgl1-mesa-dev libegl1-mesa-dev`. Ядро та його тести не потребують цих графічних залежностей.

Для збирання та тестування лише алгоритмів без SFML:

```sh
cmake -S . -B build -DPATHEXPERIMENT_BUILD_APP=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Цей варіант створює бібліотеку `pathx_core` і виконуваний файл тестів `pathx_tests`.

## Модель графа й вартості

Карта — це граф $G=(V,E)$. Кожна прохідна клітинка є вершиною $V$, а ребро $E$ з'єднує прохідних сусідів по вертикалі або горизонталі. Діагонального руху немає; степінь вершини не перевищує чотирьох.

| Місцевість | Вартість входу |
| --- | ---: |
| Дорога | 1 |
| Звичайна | 2 |
| Болото | 5 |
| Стіна | непрохідна |

Для маршруту $p=(v_0,v_1,\ldots,v_k)$ довжина дорівнює $k$ крокам, а зважена вартість становить

$$
C(p)=\sum_{i=1}^{k} w(v_i).
$$

Старт $v_0$ не додає вартості, а вхід у ціль додає вартість її місцевості. Тому довший маршрут може бути дешевшим. На схемах наведено ілюстративний приклад: 10 входів у болото коштують $10\cdot5=50$, тоді як 14 входів на дорогу — $14\cdot1=14$. Це пояснення моделі, а не виміряна статистика програми.

Під час перевірки ребра $(u,v)$ зважений пошук виконує релаксацію:

$$
g_{candidate}(v)=g(u)+w(v).
$$

Якщо значення краще, пошук оновлює `g`, записує `u` як батьківську вершину й додає новий запис до черги. Старий запис залишається та пропускається як застарілий під час вилучення. Це замінює операцію decrease-key.

## Алгоритми

| Алгоритм | Пріоритет | Гарантія в PathExperiment |
| --- | --- | --- |
| Dijkstra | $g(n)$ | мінімальна вартість |
| A* | $f(n)=g(n)+h(n)$ | мінімальна вартість |
| BFS | глибина | мінімум кроків, але не вартості |
| Greedy best-first | $h(n)$ | без гарантії мінімальної вартості |

Усі чотири алгоритми мають детермінований порядок сусідів і стабільне FIFO-розв'язання рівних пріоритетів за зростаючим номером вставлення. Однакові карта й алгоритм дають однакову трасу пошуку.

### Dijkstra

Dijkstra розгортає активний запис із найменшим накопиченим $g$. За додатних вартостей перше вилучення цілі гарантує мінімальну вартість. Без оцінки напрямку алгоритм поширюється широко. Це зважений варіант uniform-cost search із [матеріалів UC Berkeley CS188](https://inst.eecs.berkeley.edu/~cs188/textbook/search/uninformed.html).

![Dijkstra: найменше g та вибір обходу вартістю 14 замість прямого маршруту вартістю 50](docs/media/algorithm-dijkstra.svg)

[Переглянути стан пошуку в застосунку](docs/media/dijkstra-search.png)

### A*

$$
f(n)=g(n)+h(n), \qquad h(n)=|x_n-x_G|+|y_n-y_G|.
$$

Мангеттенська відстань рахує мінімальну кількість ортогональних рухів без перешкод. Кожен рух коштує щонайменше 1, тому $h$ не завищує справжню залишкову вартість. Вона також узгоджена: для сусідів $n,n'$

$$
h(n)\le 1+h(n')\le w(n')+h(n').
$$

За цієї політики закриття узгодженість усуває потребу повторно відкривати закриту вершину. A* зберігає гарантію мінімальної вартості й зазвичай спрямовує пошук до цілі. Допустимість евристики та $f=g+h$ пояснено в [матеріалах CS188 про інформований пошук](https://inst.eecs.berkeley.edu/~cs188/textbook/search/informed.html).

![A-star: поєднання накопиченої вартості g з узгодженою мангеттенською оцінкою h](docs/media/algorithm-astar.svg)

[Переглянути стан пошуку в застосунку](docs/media/astar-search.png)

### Breadth-first search

BFS розгортає всі маршрути з $d$ кроків раніше за маршрути з $d+1$. Він оптимальний, коли всі ребра мають однакову вартість. PathExperiment продовжує рахувати справжню вартість місцевості, але BFS не використовує її в пріоритеті. Результат має найменше кроків, проте може коштувати більше за результат Dijkstra або A*.

![BFS: вибір 10 кроків вартістю 50 замість 14 кроків вартістю 14](docs/media/algorithm-bfs.svg)

[Переглянути стан пошуку в застосунку](docs/media/bfs-search.png)

### Greedy best-first search

Greedy використовує лише найменше $h(n)$. Він часто швидко рухається до цілі, але $g(n)$ не впливає на вибір, тому стіни чи дорога місцевість можуть привести до невигідного маршруту. [CS188](https://inst.eecs.berkeley.edu/~cs188/textbook/search/informed.html) так само відрізняє пріоритет greedy $h$ від пріоритету A* $g+h$.

![Greedy best-first: найменше h може вести прямо через дорогу місцевість](docs/media/algorithm-greedy.svg)

[Переглянути стан пошуку в застосунку](docs/media/greedy-search.png)

## Що показує анімація

Один візуальний крок вилучає наступну активну клітинку й оцінює чотирьох сусідів. Полотно розрізняє небачені, відкриті, закриті й поточну клітинки, попередній ланцюжок батьків і фінальний маршрут. Короткі позначки відхилень пояснюють стіну, закритого сусіда або відсутність покращення. Відхилення конкретного переходу не є помилкою алгоритму.

## Результати й вимірювання

- **Steps** — кількість переходів у знайденому маршруті.
- **Cost** — сумарна вартість входу в клітинки маршруту.
- **Expanded** — кількість клітинок, розгорнутих алгоритмом, включно з ціллю.
- **Median** — медіана часу обчислення в мікросекундах.

Порівняння виконує один прогрів і 31 незалежний вимірюваний запуск кожного алгоритму. Ініціалізація пошуку та відновлення маршруту входять у вимірювання; відображення й штучні затримки не входять. Для порівняння продуктивності використовуйте Release-збірку.

## Складність

Нехай $|V|$ — кількість прохідних клітинок, а $|E|$ — ортогональних з'єднань. Для цієї сітки $|E|=O(|V|)$.

| Алгоритм | Класична складність | Фактична реалізація |
| --- | --- | --- |
| Dijkstra | $O((V+E)\log V)$ із бінарною купою | така сама, із лінивими застарілими записами |
| A* | $O((V+E)\log V)$ для цієї скінченної реалізації graph search | ті самі механізми; евристика змінює кількість розгортань |
| BFS | $O(V+E)$ із FIFO-чергою | спільна пріоритетна черга за глибиною: $O((V+E)\log V)$ |
| Greedy | $O((V+E)\log V)$ | така сама, без гарантії вартості |

Дані вершин займають $O(V)$, а ліниві записи черги можуть додати $O(E)$ пам'яті.


## Відтворення демонстрації

`PathExperiment --record-demo captures` зберігає реальні кадри SFML-вікна та порівняння. На великих картах він адаптивно пропускає частину кадрів, щоб GIF мав обмежений розмір; звичайний інтерактивний режим усе одно відображає кожне розгортання окремим кадром. `python tools/make_demo.py captures docs/media/search.gif` створює GIF; для скрипту потрібен Pillow. Використовуйте нові шляхи, щоб зберегти попередні результати. `--smoke-test captures` перевіряє введення, стан пошуку, збереження та приклади й робить нативні знімки.

Для включення нативної перевірки до CTest задайте `-DPATHEXPERIMENT_ENABLE_GUI_TESTS=ON` під час конфігурації; потрібен доступ до графічного дисплея. Повторний запуск перевірки створює новий каталог знімків і зберігає попередні результати.

## Додавання алгоритму

Алгоритми є розширеннями вихідного коду. Реалізуйте `ISearchSession`, створіть фабрику `AlgorithmDescriptor`, додайте її в `registerCustomAlgorithms()` у `src/algorithms/CustomAlgorithms.cpp` і перебудуйте застосунок. Селектор та таблиця вимірювань автоматично отримають запис із реєстру.

Межа навмисно реалізована в C++, без динамічного завантаження DLL або CLI-скриптів: сесія має надавати карту, дані вершин, події кроку, результат і попередній маршрут, необхідні візуалізатору. Повний контракт і приклад наведено в [Adding algorithms](docs/ADDING_ALGORITHMS.md).

## Архітектура й джерела

`pathx_core` містить сітку, пошукові сесії, реєстр, результати, вимірювання та зберігання без заголовків SFML. Шар застосунку відповідає за редагування, ввід, час і відображення. Так ядро тестується без вікна, а майбутній адаптер Ribterra зможе використати модель без змін її репозиторію зараз.

Докладніше: [Architecture](docs/ARCHITECTURE.md), [Adding algorithms](docs/ADDING_ALGORITHMS.md) і [Verification](docs/VERIFICATION.md). README не називає успішними неопублікований реліз або неперевірений запуск CI.
